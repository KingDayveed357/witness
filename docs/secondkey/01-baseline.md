# D1. Baseline and architecture

## What Witness already is (verified in this repo and sandbox, 2026-10-16)

Witness is a spend-control layer for AI shopping agents. It runs as a TypeScript pnpm monorepo:

- a Fastify API;
- a separate worker/executor on pg-boss;
- Postgres;
- a Next.js 16 web app with an allowlisted server-side key proxy;
- an AG Studio ops console;
- a Render Blueprint.

| Capability | Where | Verified how |
|---|---|---|
| Intent → policy (structured, or AI-compiled draft the shopper confirms) | `packages/engine/src/intents.ts`, `packages/ai` | Unit + DB tests |
| Deterministic screening (budget, retailer, size, colour, brand, market price) | `packages/core/src/checks.ts` | Unit tests |
| AI checks that can only tighten a decision: injection classifier, listing verifier; failure means HOLD | `packages/ai/src/components.ts` | Unit tests with fake + live evals (Stage 4) |
| PayPal Orders v2 `AUTHORIZE` with a vaulted sandbox buyer | `packages/paypal` | Live sandbox (S4, E2E) |
| Capture/void only in the executor (`MoneyMovementClient`, role `executor`), three-way match, deterministic request IDs | `packages/executor` | DB tests + live `cart_swap` → VOIDED |
| HOLD with one-time reviewer link, approve/deny, 72 h auto-void | `packages/engine/src/holds.ts` | S5 live, 16/16 |
| Hash-chained audit log + public verifier | `/v1/verify/*` | E2E: chain valid on every run |
| Live read-only PayPal proxy (`/v1/purchases/:id/paypal`) | `apps/api` | E2E |

## What the sprint added

Everything below is local and uncommitted until the sprint commit; nothing is pushed or deployed.

- **`packages/ai/src/manipulation.ts`**: the Second Key detector, moved from the spike into the shared engine.
  - The model returns a zod-validated tactic list with verbatim quotes.
  - Code keeps only quotes that really occur in the conversation (6 or more normalised characters).
  - A deterministic `decide()` maps the result to HOLD / VERIFY / PROCEED, and any failure becomes HOLD.
- **`checkManipulation`** in `aiScreen`: when a payment carries a `conversation`, its result is a normal `Check`. It is `unknown` (→ HOLD) or `pass`, **never `fail`**, so the trusted contact decides, not the model.
- **`PurchaseRequest.conversation`** (optional, strict, at most 60 lines of at most 1000 characters each).
- **Fixture `XFER-NEW-PAYEE`** and scenarios **`scam_transfer`** / **`benign_transfer`**. The transfer is labelled *simulated, sandbox, held by platform*.
- **Concurrency fix in `resolveHold`**: the loser of an approve/deny race now gets 409 instead of a misleading 200. Regression test in `apps/api/test/stage4.db.test.ts`.

## Architecture: one pipeline, two kinds of manipulated decision

```
                     ┌──────────── untrusted inputs ────────────┐
 human:  call audio → transcript / screenshot → conversation    │
 agent:  product listing text, checkout response                │
                     └───────────────────────────────────────────┘
                                   │
                    deterministic policy checks (amount cap, payee, retailer…)
                                   │
              AI checks (schema-validated, quote-grounded, fail → unknown)
              ai.manipulation │ ai.injection │ listing integrity
                                   │
                  screenOutcome: any fail → REJECT · any unknown → HOLD · else PROCEED
                                   │
             PayPal AUTHORIZE (money reserved, not moved)
                                   │
              HOLD → one-time link → trusted contact approves / denies / does nothing
                                   │
       executor only: capture (three-way match) │ void │ auto-void at 72 h
                                   │
           independent PayPal GET  +  hash-chained audit
```

The model can only add an `unknown`. It cannot approve, capture, change the amount or payee, or turn off a deterministic check. The executor is the only component holding capture/void credentials.

## Gaps

1. **Transfers are modelled as a product in a cart** (finding E2). Needs a `transfer` request type: payee, amount, payee novelty, channel.
2. **Trusted contact = the shopper key holder.** There is no separate reviewer identity, invitation or notification channel. The link is generated by an API call and shown on screen.
3. **No real P2P money movement.** Architecture B (platform-held authorization, then payout) is the only verified path (S4).
4. **Conversation storage.** The raw conversation is stored in `purchases.request` for idempotency hashing. For a real product: store a hash plus the grounded quotes only, with a retention limit.
5. **Speech input in the demo browser is unverified** (S3).
6. **No rate limiting on public hold endpoints**; link TTL is 72 h (E4).
